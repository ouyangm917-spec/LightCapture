# 0.4.2 截图与贴图关闭后的内存对比

## 结论

已复现图片关闭后原生位图回收滞后。三轮独立后台实验中，全部关闭 5 秒后的工作集中位数由 **225.59 MiB 降至 106.88 MiB**（下降 52.6%）；专用提交由 **182.01 MiB 降至 63.20 MiB**（下降 65.3%）。优化后约 1 秒，所有被跟踪的截图窗口、贴图窗口及位图弱引用均已失效。

这些是同场景后台实验数据，不是对用户正在运行的 319.6 MB 进程强制清理后的读数，也不等同于任务管理器默认的私有工作集列。没有停止、重启或更换用户的运行进程。

## 已确认原因

- 大图像主要使用 WPF/GDI 原生像素缓冲。关闭后托管堆只有约 1.5–1.8 MiB，后续分配很少，自动 GC/终结器不一定及时触发；原版本在关闭 5 秒后仍保留较高提交量。
- 原 `CaptureWindow.Closed` 只取消翻译和关闭工具栏，未清空整屏图、裁剪图、译图及 renderer；窗口对象短时存活会带住整个图像链。`CroppedBitmap` 与马赛克变换缓存仍引用源图。
- 贴图原本已经解绑 `Picture.Source`，并非完全没有清理；但原生对象仍可能等待回收。
- 对原版本进行单独的诊断性 GC 后，工作集降至约 106 MiB，全部被跟踪对象消失。未发现本实验中的永久引用泄漏。`Application.MainWindow` 在关闭后已为 null，最初的主窗口根引用假设被实验排除。

## 修改

- 截图关闭时释放图像字段、renderer 和工具栏/内容引用，取消未完成翻译，并阻止关闭后的重绘。
- 贴图关闭解绑原图、内容和菜单。
- 最后一个图片窗口关闭后，合并一次约 750 ms 的空闲回收。截图、贴图、GIF 或录制窗口仍存在、截图正在启动或异步图片操作仍进行时跳过；异步操作完成后重新安排。
- 原生终结器等待在后台线程执行；不周期性强制 GC，不调用工作集裁剪 API，不清空系统剪贴板。

## 对比方法

基线为源码 `094583d57bc8328df02d89249dcdbb01bcf3b968`，只增加同一份 `MemoryProbe` 和早期诊断入口，没有加入释放优化。基线程序集保留在本地 `artifacts/memory-baseline/`。

双方使用相同 .NET / Windows Desktop 10.0.14，逐个启动低优先级独立进程，各测 3 次。每次通过实际 `ScreenCaptureService.ToSource` 创建 3 张 3840×2160 合成图片，经实际截图窗口、1920×1080 选区、渲染及贴图窗口的生命周期，再全部关闭。控件仅离屏绘制；不调用 Show、不创建 HWND，不读取桌面、不注册热键、不操作剪贴板。

记录工作集（WorkingSet64）、专用提交（PrivateMemorySize64）、窗口数及弱引用存活数。先记录自然关闭后 1 秒和 5 秒，再执行双方完全相同的诊断性 GC。表内优化后读数包含新版本正常的自动空闲回收，不使用后续诊断 GC 的结果冒充自然回落。

| 阶段（三次中位数） | 原版工作集 MiB | 优化后工作集 MiB | 原版专用提交 MiB | 优化后专用提交 MiB |
| --- | ---: | ---: | ---: | ---: |
| 探针初始化 | 45.44 | 45.29 | 13.55 | 13.32 |
| 截图关闭、3 张贴图保留 | 205.19 | 205.18 | 165.50 | 165.07 |
| 全部关闭 1 秒 | 225.52 | 106.56 | 182.01 | 63.14 |
| 全部关闭 5 秒 | 225.59 | 106.88 | 182.01 | 63.20 |
| 额外诊断 GC 后 | 106.02 | 107.23 | 61.55 | 63.27 |

关闭 5 秒的逐次结果：原版工作集 **226.56 / 225.59 / 225.01 MiB**，优化后 **106.88 / 107.34 / 105.48 MiB**；原版专用提交 **183.92 / 182.01 / 181.46 MiB**，优化后 **63.45 / 63.20 / 61.20 MiB**。

## 验证及边界

- 20 项核心、7 项 Python、18 项原生后台检查通过。原生检查覆盖异步图片操作、贴图、录制/GIF 窗口的活动保护与关闭后回收。最后一张贴图关闭后窗口与位图全部可回收。
- 当前结果不能覆盖真实桌面合成器、混合 DPI、系统剪贴板持有图片及长期使用后的所有缓存。没有通过清空剪贴板或干预用户运行进程制造低占用。
- 回落后的进程仍包含运行时及已加载的界面资源，不能承诺恢复到刚启动时的数值。实际运行占用需用户自行退出旧版、启动新版后再用相同口径观察。
